# In-app llama.cpp on the iQOO phones (2026-10-10)

The numbers below were taken through the app itself: SwarmOS launches `libllama-server.so` and `librpc-server.so` from `nativeLibraryDir` as child processes and talks to them over loopback HTTP (`LlamaRuntime`, `LlamaServerClient`). Benchmarks run through the same client path the other modules use (streamed `/v1/chat/completions`), triggered by the signed route `POST /v1/models/bench` or the Models screen.

## Setup

- App: branch `worktree-agent-aa99845b05540ffdd`, base id `com.swarmos.app`, debug build. Binaries are the `i8mm` build from `native/prebuilt/arm64-v8a/` (llama.cpp v0.6.0, `libllama-server.so` sha256 `c3d74d629ac6a82c...`, 10.5 MB; `librpc-server.so` 1.5 MB).
- Chat server (final flags, following `docs/llama-server-api-notes.md`; context is 8192 total instead of 4096 because Choir/Data Union prompts can pass 2048 tokens): `libllama-server.so -m <models dir>/Qwen3.5-4B-Q4_K_M.gguf --host 127.0.0.1 --port 8080 -t 6 -c 8192 -np 2 --reasoning off --no-webui`. The benchmark and sustained rows in the table below were taken with the first flag set (`-t 6 -c 8192 -np 1 --jinja`, thinking switched off per request with `chat_template_kwargs`); the A selftest and the Gemma check on C used the final set. Decode does not depend on `-np` for a single request.
- Embedding server: `--embedding -t 2 -c 4096 -np 2 -b 2048 -ub 2048` on `embeddinggemma-300M-Q8_0.gguf`, port 8081 (768-d, truncated to 256 and re-normalised by the client).
- Models: `/sdcard/Android/data/com.swarmos.app/files/models/`, pushed with `adb push` (3 MB/s over wireless ADB: 14 min per 2.7 GB file). SHA-256 and sizes pinned in `docs/models.md`; the app checks size, `ModelStore` verifies SHA-256 on download.
- Benchmark = one streamed chat request, 512 prompt tokens (exact, counted by the server; the first two rows used an older 425-token prompt), 128 generated tokens (`ignore_eos`), `cache_prompt=false`, temperature 0. Prefill tok/s = prompt tokens / `timings.prompt_ms`, decode tok/s = 128 / `timings.predicted_ms`. RSS is VmRSS of the server process from `/proc/<pid>/status`.
- Thermal: `PowerManager` status (NONE, LIGHT, MODERATE, SEVERE, CRITICAL). The phones were charging on the PC (AC powered) for all runs. Rows marked "start n/r" were taken before the app recorded the starting status; only the end status is known.
- Other load on the phones during the runs: B had the link worker's app (idle, 10% CPU) and, later, other workers' variants; C was running the native worker's `llama-bench` and a 4B server at the same time for all of my C numbers (contended); A ran the native worker's 8-thread soak server (186% CPU) during the A selftest.

## 10-minute test with the screen off and the app in the background

Procedure: `input keyevent KEYCODE_HOME`, `KEYCODE_SLEEP`, no system settings changed. Evidence is the ActivityManager events buffer (`logcat -b events`).

| Test | Result |
|---|---|

| B, loaded (sustained bench running), screen on, another worker's app in front | Alive at 02:15:22, past the 02:15:08 grid point |

The kill lines (phone B, identical shape both times, 15 minutes apart):

```
01:45:08.153 am_app_frozen   [0,10346,com.swarmos.app,from pem_freezer]
01:45:08.169 am_proc_died    [0,22268,com.swarmos.app,200,4]
01:45:08.170 am_foreground_service_stop [... com.swarmos.app/.core.SwarmService ... STOP_SERVICE]
02:00:08.348 am_app_frozen   [0,10346,com.swarmos.app,from pem_freezer]
02:00:08.373 am_proc_died    [0,30709,com.swarmos.app,200,4]
```

Reading: OriginOS's `pem_freezer` freezes the app and the process dies 16-25 ms later, with the foreground service running and a partial wake lock held. The two kills are exactly 15 minutes apart (01:45:08, 02:00:08), and each was the first point of that 15-minute grid after the screen went off; the grid point 02:15:08 passed without a kill on both A and B. The scan interval itself is an inference from two events. Both servers are children of the app and die with it, so an in-process JNI runtime would die the same way; it would not be a fix. What the data supports: a loaded (generating) app in the background with the screen off is killed at the next grid point; idle servers survived two grid points; a loaded phone survived a grid point with the screen on. Not tested: the battery-limit exemption that the first-run screen asks for ("Turn off battery limits"), a foreground activity with the screen on across a full 15-minute scan under load. A third death was seen on C at 02:04:44 (`am_proc_died` adj 200, no `pem_freezer` line, no lmkd line) four seconds after a selftest finished with Gemma 4 E4B (6.4 GB) and the embedder resident; the service restarted itself (`START_STICKY`) and auto-loaded the last chat and embedding models again.

## Review fixes (JVM tests only, no phone run)

Checked by unit tests, not on a phone: at 2026-10-10 (after the review commit) phone A was at Thermal Status 2 with another worker's standalone `llama-server` (pid 18197, port 18080) running, and phone B is reserved, so no server was started anywhere for these changes.

- `chat()` and `embed()` cancel: `ClientCancelTest` runs a local server that accepts the request and never answers; `withTimeout(600 ms)` around `chat`, `chatStream`, `embed` and `withChatBudget(600)` all return on time and the server sees the connection close (the signal llama-server uses to free its slot). A budget without `withTimeout` ends on the socket read timeout.

## GPU build for the chat model (design; the phone run is in the next section)

Change (from `docs/benchmarks/2026-10-10-throughput-tuning.md`, decision 1): the chat server starts on the OpenCL (Adreno) `libllama-server`, shipped as `libllama-server-gpu.so`, with `-ngl 99 -t 4 -c 8192 -np 2 --reasoning off`, and falls back to the CPU i8mm build (`-t 6`, unchanged) when the GPU server does not get READY within 120 s, exits while starting, or its first request fails. The embedder, `rpc-server` and a split chat server (`--rpc` in the arguments) stay on the CPU build. `ServerStatus.backend`, `GET /v1/models/state` (`roles.chat.backend`, `useGpu`) and the Models tab say GPU or CPU. Settings: "Use GPU for chat" (default on), `POST /v1/models/gpu {"enabled":false}`, `--ez gpu false`. Scheduler capacity is 1 while chat is READY (the server keeps two slots).

Written before the phone run; checked by JVM tests only at that point (`BackendPlanTest`: backend order, CPU for embedder, rpc and split, GPU and CPU command lines, capacity 1). The device queue was held by the MemoryCloud worker (marker `base-id-owner.txt` said "memcloud" from 03:37 to at least 05:00, a standalone `rpc-server` ran on phone A until 04:25) and the end-to-end check queue was waiting for it as well, so nothing was installed on phone A. No GPU number exists yet; the CPU rows above are the only in-app numbers. Commands for the run, on phone A with the marker free, no llama or rpc process (`pidof`) and Thermal Status 0 or 1:

1. `adb -s 192.168.242.89:5555 install -r app/app/build/outputs/apk/debug/app-debug.apk`, then `am start -n com.swarmos.app/com.swarmos.app.MainActivity`.
2. `GET /v1/models/state` until `roles.chat.state` is READY; `roles.chat.backend` must say GPU. `adb shell run-as com.swarmos.app grep -i -E "opencl|offloaded|adreno" files/logs/chat.log` shows the layers on the GPU.
3. `POST /v1/models/bench` once from the cool start (prefill, decode, time to first token, `rssMb`, `thermalStart`, `thermal`), then `POST /v1/models/selftest` and poll `GET /v1/models/selftest` (schema 10 of 10, 256-d unit vectors from the CPU embedder running beside it).
4. `adb shell run-as com.swarmos.app kill -9 <pid of libllama-server-gpu.so>`: expect the banner "The server was killed (killed by signal 9 ...). Restarting in 2 s.", READY again on the GPU, `restarts: 1`.
5. `POST /v1/models/stop {"role":"all"}`, delete the marker.

### Why the GPU server did not start, and the fix that worked

The exec'd child stopped with `CANNOT LINK EXECUTABLE ".../lib/arm64/libllama-server-gpu.so": library "libOpenCL.so" not found: needed by main executable`. Reproduced on C as the app uid (`adb shell run-as com.swarmos.app`, same binary, same `lib/arm64` directory):

| Experiment | Result |
|---|---|
| `LD_LIBRARY_PATH=<nativeLibraryDir>` (what the app set before) | `library "libOpenCL.so" not found: needed by main executable` |
| `LD_LIBRARY_PATH=<nativeLibraryDir>:/vendor/lib64:/system/vendor/lib64` | links and runs (`version: 0.6.0-dev (build 1, commit d812350)`), and the full server then runs on the GPU |
| `LD_PRELOAD=/vendor/lib64/libOpenCL.so` | refused: `library "/vendor/lib64/libOpenCL.so" ... is not accessible for the namespace "(default)"` (permitted paths: /system/lib64, /system_ext, /data, /apex/..., not /vendor/lib64) |
| `/system/bin/linker64 <binary>` with the vendor `LD_LIBRARY_PATH` | also works, not needed |

The exec'd child is linked in the linker's `(default)` namespace. The manifest `uses-native-library libOpenCL.so` only opens the library to the app's own class loader. Directories named in `LD_LIBRARY_PATH` count as accessible in that namespace, an absolute `LD_PRELOAD` path outside the permitted list does not. Fix (first alternative, no JNI shim and no linker64 needed): `LlamaArgs.ldLibraryPath` gives the GPU chat build `<nativeLibraryDir>:/vendor/lib64:/system/vendor/lib64`; every other child (CPU build, embedder, rpc-server) keeps the native library directory only. CPU fallback unchanged. `/v1/models/state` now has `roles.<role>.lastError`: the last stderr/log lines (whole lines, at most 2 KB) of a failed or fallen-back start or of a server that died, with the exit description as its last line; `null` after a clean start.

### Evidence that the in-app server runs on the GPU

- `GET /v1/models/state` after the app start: `roles.chat.backend` = `GPU`, state READY, pid 28158, `rssMb` 814 (loadMs 24157 on the first start with a cold file cache, 13327 on the second).
- The process has `/dev/kgsl-3d0` open and `/vendor/lib64/libadreno_compiler_cl.so` mapped (`/proc/<pid>/fd` and `/proc/<pid>/maps`, read with `run-as`). Command line: `libllama-server-gpu.so -m .../Qwen3.5-4B-Q4_K_M.gguf --host 127.0.0.1 --port 8080 -ngl 99 -t 4 -c 8192 -np 2 --reasoning off --no-webui`.
- The in-app server log is terse (no tensor-load lines). The layer line comes from one extra start of the same binary with the same environment and `-lv 4` on another port (as the app uid, model read from `/data/local/tmp/llama/models/`): `load_tensors: offloaded 33/33 layers to GPU`, `load_tensors: OpenCL model buffer size = 2603.62 MiB`, `using device GPUOpenCL (QUALCOMM Adreno(TM) 840)`, `ggml_opencl: OpenCL driver: OpenCL 3.0 QUALCOMM build: 0842.13`.

### In-app benchmark, GPU against CPU on the same phone and session (POST /v1/models/bench, 512 prompt tokens, 128 generated, cache off)

| Backend | Flags | Prefill tok/s | Decode tok/s | Time to first token | Server RSS (peak) | Thermal start / end |
|---|---|---:|---:|---:|---:|---|
| GPU (OpenCL, Adreno 840) | `-ngl 99 -t 4 -np 2` | 201.9 | 17.31 | 2.59 s | 1032 MB (1033) | NONE / NONE |
| CPU (i8mm) | `-t 6 -np 2` | 71.6 | 16.47 | 7.20 s | 5952 MB (5952) | NONE / NONE |

One run each: GPU first, from a cool start; CPU about 2 minutes later, after the selftest, a kill test and a reload (status still NONE). Prefill is 2.8 times faster and the process 5.8 times smaller on the GPU; decode is within 5 % (17.3 against 16.5). `docs/benchmarks/2026-10-10-throughput-tuning.md` measured GPU decode at 13.3 to 13.5 tok/s, and the server's own log of the 165-token selftest answer on this GPU server shows 13.77 tok/s, so decode on the GPU varies between runs (13.8 to 17.3 here); a single in-app run should not be quoted as better than the native note's mean. The CPU process RSS includes mapped model pages; the GPU process holds the weights in GPU buffers.
