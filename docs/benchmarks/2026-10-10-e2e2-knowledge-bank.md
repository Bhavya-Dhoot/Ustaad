## Things that did not behave as documented, or that the procedure does not cover

1. **Replication on its own.** The document says peers sync when a peer comes online and every 3 minutes. A card saved and shared on B while C and A were online had not reached C after about a minute, and the revocation had not reached C after a minute either. It did arrive by itself on **Phone A**: when I looked, at about 08:55, A held the card with the revocation set (`revokedMs` 08:31:34) although no sync was ever called towards A; the time it took was not measured. So the mechanism works (card and tombstone both spread, probably through the 3-minute timer or through C offering them on), but a presenter cannot count on it inside the first minute; the explicit sync is the only deterministic path.
2. **Provenance is not in the ask report.** The saved answer comes back with `fromCard` and the answer text only; `sources` is empty (as documented), so the author, date and cited files of the card are not part of the answer response. They are in the card view (`GET /v1/kb/cards` on C): author "Phone B", created 08:29:04, sources Phone B IMG_2231.jpg, Phone A Laptop_Extended_Warranty_Certificate.pdf, Phone B IMG_2238_Washing_Machine_Warranty_Card.jpg, Phone B "(private file on this phone)", audit hash `0c5525fe07...`. Whether the Data tab shows that block next to a saved answer was not checked (no screen).
3. **The saved text refers to source numbers that no longer exist.** The card text is the original answer ("... located in source [1] as WARRANTY BILL - LAPTOP on Phone B. It also references an extended warranty certificate in source [2] on Phone A"), shown with no source list in the ask response, so "[1]" and "[2]" point at nothing in that response.
4. **A card with a private source was saved from a real answer.** The real answer's fourth source was "(private file on this phone)" from B's Private folder; the debug save route took the sources as given (`priv: false` is what my helper sent for every source, because the ask report does not say which source is private), so the card was saved as SWARM and shared although one of its listed sources is a private file of B (title replaced, no text). The app's own save button would refuse this case ("A card with a source in a private folder cannot be shared"); the debug route only refuses what the caller marks `priv: true`. My helper should set `priv` for sources titled "(private file ...)"; it did not.
5. The 35 ms answer is the card lookup alone: no peer was queried and no model ran, so there is no GPU or network time in it.
6. Phone A was online during the whole step and is also where the replicated card ended up; the audit logs of A were not read.
