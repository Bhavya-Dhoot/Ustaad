## Deviations, failures and anything that looked wrong

**F1. The GPU chat server did not start on either phone; the CPU build ran everywhere.** `roles.chat.backend` was `CPU` in every read of `/v1/models/state` I looked at on A and on C (05:26 onwards), with this notice (truncated by the app at 160 characters): `The GPU server failed (exited with code 1 during start; last log: CANNOT LINK EXECUTABLE ".../lib/arm64/libll). Running on the CPU build.` I reproduced the full linker message on A by running the shipped binary under the app's own uid (`run-as com.swarmos.app <nativeLibraryDir>/libllama-server-gpu.so --version`): `library "libOpenCL.so" not found: needed by main executable`. `/vendor/lib64/libOpenCL.so` exists on the phone, so the app's linker namespace does not expose it (inference: a `<uses-native-library android:name="libOpenCL.so" android:required="false"/>` entry in the manifest is the usual remedy on Android 12 and later; not tried, source not edited). The same message was not reproduced on C, only the same truncated notice. Every number in the three notes is therefore a CPU number.

**F2. The Choir answers are poor with the real model, and the single run passed its infrastructure check while giving a wrong final answer.** In the single run (table above) both lanes answered with the real model, yet R1 gave `After calculating ... total is 4` (a sentence cut at 60 characters; the model's own steps say 484, the true value is 486) and `math` with confidence 0.0, and in R2 both phones answered `,`. The two lanes agreed on `,` ("unanimous but unverified", method MAJORITY, tool check NOT_CHECKABLE). The script printed PASS for `d-choir-run` because that check only asserts real model, both lanes answered, a final answer present; a stricter check `d-choir-answer` (final answer equals the known answer) was added afterwards and would fail for this run. In the evaluation the same pattern shows up: answers that are a single punctuation mark (`,` `:` `}` in m4 and p2), prose in the answer field (`And 126 * 9 = 1134` for m1, a sentence cut at 60 characters for p1), and answers wrapped in braces or as an expression (`{155.5}`, `{240}`, `{800 * 1.25 * 0.80}`). The app's scorer counts `{240}` and `{800 * 1.25 * 0.80}` as correct (it evaluates them), so two of the three MATH rows the choir arm gets right (p1, p2) are brace or expression answers; read those cells as "the scorer accepted it", not "the model wrote 240". The second round did not repair anything in the single run (both phones answered `,`); mean rounds in the evaluation were 1.8.

**F3. The tool check almost never fires without the problem's own test.** Verified 1 of 10 (m2, basis "model-expression"), 0 against a problem test (that option was off, as asked), so the "choir + tool check" arm equals the "choir" arm here (7 and 7). The comparison the PRD wants (tool-verified against the problem test) needs a second pass with that option on.

**F4. Phone A throttled hard as coordinator.** A started both slices at Thermal Status 1 and peaked at 3 in each (C peaked at 1 and 0). The app refuses an eval from status 3 up. The guard then waited about 15 minutes (slice 2, first attempt) and about 2 minutes (slice 2, second attempt) for A to fall to 1, and unloaded the model servers after 3 minutes. Slices took 356 s and 338 s for 5 problems each (about 70 s per problem with the three-samples arm).

**F5. The evaluation is incomplete: 10 of 20 problems.** (a) At about 05:47 an HTTP request to both phones from this PC returned nothing (HTTP 000) while the guard was reloading the models (both answered again at 05:47:48); the first attempt at slice 2 was aborted with "models not ready" before anything ran, and the script went on to the Data Union and throughput steps. The slice was repeated at 06:13 with `--resume` (and the script now retries GETs that fail at the transport level). (b) At 06:22:21 phone A's Wi-Fi switched on its own from the access point "Chulbul" (192.168.242.x, where the PC and C are) to the saved network "iQOO" (192.168.112.185, not reachable from this PC or from C); `dumpsys wifi` shows `CMD_START_CONNECT ... "iQOO"` issued by uid 1010 (the system) followed by a locally generated disconnect from "Chulbul". A stayed there until at least 06:36 and was reachable only over USB. Slice 3 never started (the guard waited 5 minutes for a thermal reading that could not be taken), so the script was stopped at about 06:35. Phone A was not moved back: that would change a phone Wi-Fi setting.

**F6. Phone C's lane produced no usable answer on two of ten problems.** `nodesAnswered` is 1 of 2 for m1 and m4, so those choir rows are in effect one-phone rows; the reason (timeout, parse failure or error) is not in the eval rows and was not captured.

**F7. How to read the arm table.** n = 10, so one problem is 10 points: choir 7 against one phone 4 and three samples 6 are differences of 3 and 1 problems. On wall-clock per problem, choir (27.8 s) took less than three samples (39.6 s) and more than one phone (14.5 s). The PRD asks for claims about throughput and verification, not "smarter"; these numbers support neither a clear accuracy claim nor a verification claim yet.

**F8. Foreground.** The `.link` variant of another worker came to the front on both phones at least once during the run (seen at 05:24 and 06:13); the base app was brought back each time. A base app that is not in front risks being frozen by OriginOS.

**F9. The pairing secret.** See the header: both phones ran on the same rotated secret, not the dev secret. At the end of the run both were put back on the dev secret with the `swarmos://pair` deep link (A given a payload naming C, C a payload naming A); both then answered a request signed with `swarmos-dev-secret`.
